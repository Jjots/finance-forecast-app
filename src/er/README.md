## Как читать схему

Две рамки соответствуют отдельным экземплярам PostgreSQL (`db_main`) и TimescaleDB (`dwh`). Линии внутри рамки показывают внешние ключи, пунктир между рамками — сопоставление идентификаторов приложением. Для каждой связи кратность читается у обоих концов. Тип и допустимость NULL указаны у каждого поля согласно легенде. Уникальные ограничения и индексы перечислены внутри соответствующих таблиц. Индекс первичного или уникального ключа обеспечивает и поиск по его ведущим полям.

## Проектные решения

| Сценарий | Как устроены данные и почему |
|---|---|
| Вход и управление доступом | Запись пользователя связана с ролью. Четыре роли проекта — аналитик, инвестор, риск-менеджер и администратор. Перечень разрешённых действий хранится по ролям. При изменении права Backend получает его для всех пользователей этой роли. Настройки вынесены в отдельную запись с ключом пользователя. |
| Компания и модель | У каждой модели есть компания и целевой показатель. Новое обучение создаёт версию той же модели. Реестр ML хранит обученный артефакт, а Backend использует метаданные версии для истории и выдачи результатов. |
| Прогноз на несколько дат | Заголовок прогноза связывает пользователя с версией модели. Отдельные строки содержат точки горизонта. Один расчёт на три даты сохраняется как один заголовок и три точки. Через версию определяются компания и показатель даже после появления следующей версии. |
| Поступление данных | Scheduler получает отчётность РСБУ, данные Банка России и MOEX. Backend нормализует батч, записывает наблюдения через `ts_repo_comp` и фиксирует статус загрузки через `db_repo_comp`. Это операции в двух БД. После сбоя между записями повтор батча должен быть безопасен. |
| История и аналитика | В DWH источник, показатель и серия дают контекст числу. Ключ наблюдения включает серию и время, по которому разбита гипертаблица. По этому же ключу Backend обновляет исправленное значение. Для отбора истории за период используется индекс с серией перед временной координатой. |

### Почему два хранилища

При сохранении прогноза важно одной транзакцией связать его точки с заголовком и сохранить ссылку на существующую версию модели. Для этого подходит PostgreSQL с обычными таблицами, составными ключами и проверкой ссылочной целостности. Другой характер работы возникает, когда нужно прочитать историю котировок за год. В TimescaleDB наблюдения группируются по времени, а запрос выбирает нужные серии и интервал. Даты финансовой отчётности и моменты торгов хранятся с разной точностью. День загрузки не должен сдвигать отчётный период или менять идентичность наблюдения.

### Граница двух БД

Пример: Backend принимает данные компании, находит её в `db_main.companies`, сопоставляет внешний код источника с устойчивым `company_id` и затем пишет серию и наблюдение в DWH. Если компанию не удалось определить однозначно, загрузчик должен отложить запись до разбора. Для общего макропоказателя, например ключевой ставки, компания не требуется. При изменении названия компании связь по идентификатору сохраняется. Удаление компании с историей требует согласованной политики двух хранилищ.

На рисунке три логических сопоставления. Кроме компании в `series.company_id`, модель в `models.metric_code` использует код из `dwh.metrics`, а журнал загрузок в `ingest_batches.source_code` — код из `dwh.sources`. Backend сверяет эти коды до записи. Изменение смысла кода требует нового кода, иначе исторический прогноз получит другую интерпретацию.

### Детализация и ключи

Для пользователя принята одна роль в каждый момент. Пара `(role_code, permission_code)` задаёт назначение права роли и позволяет выдать то же право нескольким ролям. Ключ `user_settings.user_id` одновременно ссылается на профиль и допускает только один набор индивидуальных настроек. При отсутствии записи применяются настройки приложения.

В прикладной БД компания задаётся один раз на уровне `models`. У прогноза составная ссылка `(model_id, version_no)` фиксирует версию. Частичный уникальный индекс версий с условием `is_active` допускает максимум одну активную версию каждой модели. В одной транзакции Backend сохраняет заголовок и точки, проверив, что число различных целевых дат равно `horizon`, даты следуют за `as_of_date` с шагом `models.step_unit`. Эти правила проверяются для всего набора точек, FK обеспечивает существование самого заголовка. Для опубликованного прогноза компания, показатель и шкала времени модели сохраняют значение на дату расчёта.

В DWH `series` задаёт паспорт ряда. `subject_key` описывает объект наблюдения, `grain` — периодичность и способ отсчёта периода. При загрузке `source_series_key` получают из устойчивого ключа поставщика либо формируют канонически из его измерений, включая объект, показатель, единицу и периодичность. Он уникален в пределах источника. Обыкновенная и привилегированная акции имеют разные идентификаторы инструмента. Курс USD/RUB хранится отдельной серией с фиксированным направлением и масштабом котировки. Каждая метрика имеет фиксированную единицу измерения.

| Проверочный пример | Ожидаемый результат |
|---|---|
| Источник повторно прислал выручку за квартал | Для той же серии и `observed_on` используется `ON CONFLICT (series_id, observed_on) DO UPDATE`. `received_at` обозначает момент приёма и может измениться. Число наблюдений сохраняется. Гипертаблицы хранят последнюю принятую редакцию значения. |
| В один день закончились IV квартал и финансовый год | Отчёты за квартал и год получают разные серии за счёт `grain` в каноническом ключе. Для поточных величин `period_start` фиксирует начало интервала, `observed_on` — его конец. Для моментного остатка или точечного макропоказателя начало может быть NULL. |
| MOEX прислала две минутные цены | Для выбранного инструмента, рынка и типа цены одна строка соответствует одному интервалу серии. Ключ `(series_id, observed_at)` различает моменты. Сделки внутри одной метки агрегируются до выбранной частоты перед загрузкой. |
| Нужна история выручки за год | Backend находит серии по компании, метрике и частоте, затем выбирает диапазон из `dated_observations` по ведущему `series_id` и датам. Для котировок ту же роль играет PK с `observed_at`. Обе гипертаблицы разбиты только по своей временной координате. |
| Нужен сохранённый прогноз при недоступности ML | Backend отбирает модели компании и показателя с нужным шагом, ищет прогноз по модели, горизонту и дате расчёта, затем читает точки по `forecast_id` в порядке `target_date`. Версия остаётся той, что сформировала этот прогноз. |

Для денежных и расчётных значений принят точный тип `numeric`. ИНН хранится текстом, что сохраняет ведущие нули. Уникальный индекс по `lower(email)` учитывает регистр единообразно при входе, индекс по `lower(company_name)` с `text_pattern_ops` поддерживает поиск по началу названия. Граница горизонта 1–60 шагов и выбор одной роли на профиль приняты для этой логической модели.

### Согласование с C4

- [L2 Игоря](../l2-containers/igor-containers.puml) и [решения ЛР4](../lab4/ARCHITECTURE_DECISIONS.md) определяют границы хранилищ. [Сценарий доступа Игоря](../lab4/igor/README.md) показывает чтение и запись через Backend и чтение из DWH со стороны ML.
- В [L3 основной БД](../l3-components/igor-db-main-components.puml) перечислены пользователи, каталог, настройки и метаданные моделей. [L3 Backend](../l3-components/diana-components-backend.puml) дополнительно описывает историю прогнозов и статусы загрузок. ER-модель уточняет хранение обоих результатов внутри `db_main`.
- По [L3 ML](../l3-components/diana-components-ml.puml) файл обученной модели и выбор активной версии принадлежат ML-сервису. Backend получает сведения через API и связывает сохранённый прогноз с версией. При инференсе и обучении ML читает историю из DWH. Историческое обозначение `api_backend` на схеме ML соответствует `backend` в решениях ЛР4.
- В [L3 DWH](../l3-components/igor-dwh-components.puml) `dwh_ingest_comp` пишет наблюдения, `dwh_query_comp` читает их, `dwh_continuous_agg_comp` рассчитывает производные агрегаты, а `dwh_retention_comp` задаёт срок хранения. Это компоненты и механизмы СУБД. RabbitMQ передаёт задания на фоновую обработку.

## Воспроизведение изображения

Из корня репозитория запустить PlantUML с поддержкой Graphviz. Файл содержит полное описание диаграммы и открывается автономно.

```powershell
$svgDir = (Resolve-Path 'docs/images/er').Path
java -jar plantuml.jar -charset UTF-8 -checkonly src/er/finance_forecast_er.puml
java -jar plantuml.jar -charset UTF-8 -tsvg -o $svgDir src/er/finance_forecast_er.puml
```

Для главы 4 вставьте SVG в Word через «Вставка → Рисунки». Векторное изображение можно увеличить, сохранив читаемость названий и ключей.
